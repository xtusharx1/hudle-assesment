# End-to-end QA audit — 14 November 2026 (IST)

This is an evidence-based audit of the local assessment app, not a claim that software can be certified bug-free. Findings below distinguish browser reproduction, real-MySQL regression tests, and code-review hardening. The original 23 tests passed before this audit; exploratory testing and additional regressions exposed gaps they did not cover.

## Environment and data safety

- App: `http://localhost:8080`, NestJS API on 3001, MySQL 8.4 in Docker.
- Browsers: the connected embedded browser with explicit viewport overrides, plus a separate native Chrome QA tab for date controls and partner login. Existing Chrome user tabs/forms were left untouched; the temporary Chrome tab was closed afterward.
- Responsive checks: 320×740, 375×812, 768×1024, 1280×900 on venue details and profile. All 18 original venue pages plus the QA venue received a mobile smoke check at 375px.
- Browser mutations used the fictional `QA Audit Court` and `QA Tester` account. The QA booking was cancelled; its history remains. The fixture venue was deactivated after testing. Existing demo bookings were not cancelled or reset.
- Destructive automated tests ran only in `hudle_test`, guarded by the `_test` database-name requirement. The normal app database was not reset.

## Additional resilience changes

These are review-driven safeguards, not separately claimed browser-reproduced bugs:

- Coordinate customer refreshes across supporting browser tabs using Web Locks; retain single-flight protection within a tab. This reduces old-refresh-token races. The fallback remains per-tab single-flight in browsers without Web Locks; that compatibility limit is explicit.
- Do not discard a signed-in identity merely because a refresh/focus check receives a temporary network/5xx error. Only an actual unauthorized response expires identity.
- Bound API fetches to twenty seconds so an unresponsive server cannot leave a loading overlay open indefinitely. A timed-out booking can still have committed; the customer should check My bookings before retrying. POST idempotency remains a follow-up item.
- Treat SQL LIKE wildcard characters as literal search text. A regression verifies `%` does not match the entire catalogue.
- Loading skeletons expose a screen-reader status. Validation/not-found errors no longer incorrectly suggest every problem is a connection failure.

## Remaining limits / release work

These are explicit remaining capabilities or verification limits, not hidden “passed” checks:

1. **Email/mobile verification and password recovery are absent.** Contacts are user-entered. This is not ready for a public launch without a verified recovery flow.
2. **Admin booking lists cap at 500 records with no pagination.** Small demo data was tested; large-history navigation remains unimplemented.
3. **Venue deactivation is one-way in the UI.** Reactivation needs an explicit supported action; deactivating the QA fixture does not erase its history.
4. **No payment collection, holds, notifications or multiple courts per venue.** These remain assessment scope limits.
5. **No POST idempotency key or bounded deadlock retry policy.** Unique occupancy is protected, but retry/recovery semantics need further production work.
6. **Rate limiting is process-local, admin auth is a single environment account, expired sessions are not automatically pruned.** Distributed/operational hardening remains.
7. **Browser compatibility is not exhaustively certified.** No separate Firefox, Safari/iOS/Android device lab, formal assistive-technology pass, long-duration soak/load run or external security penetration test was available in this audit.
8. **Historical guest bookings remain admin-visible only.** They are deliberately not claimable by unverified phone/email.

A clean pass means the enumerated checks passed on this build. It does not establish that every possible bug has been found.
